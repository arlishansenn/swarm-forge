## Context

`open-dashboard.sh` 今天的执行顺序是：读 `dashboard-url` → HTTP 可达性（建隧道，或打
tailnet IP）→ pid / `--serve` 归属检查 → cmux。

这个顺序在 issue #78 加 `--tailnet` 时是刻意保留的：当时的目标是「不带 flag 的 ssh 路径
行为一字不变」，所以没有动既有的块序。代价现在看清楚了——归属检查才是唯一能识别「swarm
没在跑」的那一步，而它排在可达性之后，永远轮不到它说话。

`stop swarm` 删 `pack_web.pid`，但**不删** `dashboard-url`。所以停机后：读端口成功、可达性
失败、归属检查（本该报 `3`）够不着。

在效的 ADR：`adr/0001`、`adr/0002`、`adr/0003`，三条与本 change 均无关，不提议改动。

## Goals / Non-Goals

**Goals**

- 停机的项目在两条路径上都报 `3` `STOPPED`。
- `--tailnet` 的「端口未发布」提示只在真的没发布时出现。
- `4` `DRIFT` 与成功路径行为不变。

**Non-Goals**

- 不让 `dashboard` 代为启动 pack_web 或 swarm。
- 不改 `stop swarm` 是否该删 `dashboard-url`。留着它是有意的（别的 verb 靠它读端口），本
  change 只要求 `dashboard` 别把陈旧文件当成「服务应该在」。
- 不动隧道回退到空闲端口的逻辑。

## Decisions

**把归属检查整块前移，而不是在可达性失败时补一次判断。** 后者要在两条失败分支各写一遍，
两份判断迟早分叉；前移之后只有一条路径，且顺序本身就表达了优先级：先问「它该在跑吗」，
再问「它可达吗」。这也让 `4` `DRIFT` 提前——端口被别的项目占用时，现在会在建隧道之前就
拒绝，比之前更早停手。

**代价，明写：** 不带 `--tailnet` 的 ssh 路径，其归属检查现在发生在建隧道之前。issue #78
当时保留旧序是为了「ssh 路径逐字节不变」，本 change 有意打破那一点——因为那次保留正是这
个 bug 的来源。可观察的差别只有一个：一个会被 `4` DRIFT 拒绝的项目，现在不会先留下一条
ssh 隧道。那是改进，不是回归。

**「已发布 vs 未发布」用 `tailscale serve status` 判别，而不是猜。** 只在可达性已经失败、
准备写报文时问一次，成功路径不付这个代价。读 serve 配置不需要 root（写才需要，见 issue
#78 的 6a），所以这一次额外查询不引入权限要求。

**判别失败时，报文退回中性说法。** 如果连 `serve status` 都读不到，报文只说端口不应答、
列出两种可能，不猜是哪一种——不确定时给一条错误建议，比不给建议更糟。

## Risks / Trade-offs

- [多一次远端查询] -> 只在失败路径上发生，成功路径不受影响。
- [ssh 路径的块序变了] -> 上面已明写；既有的 `4` DRIFT 用例与成功用例都必须保持绿，作为
  没有回归的证据。
- [`serve status` 输出格式变化导致判别失灵] -> 判别失败时退回中性报文，不会因此给出错误
  建议；最坏情况是回到「只说不通，不说为什么」。

## Migration Plan

无迁移。行为改变只发生在此前会报 `5` 的失败路径上。回滚即还原两段的顺序与那次判别。

## Open Questions

- `stop swarm` 要不要顺手删掉 `dashboard-url`？删了能让「读端口」这一步自己失败，从而更早
  报 `3`。但别的 verb 依赖这个文件读端口，本 change 不动它；如果以后发现陈旧 `dashboard-url`
  在别处也造成误判，再单独决定。
